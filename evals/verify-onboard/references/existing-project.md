# 기존 프로젝트 온보딩

## 기준 상태 파악

기존 지식·프로젝트 지침, README, 패키지·잠금 파일, 실행 스크립트·CI와 관련 진입점을 확인한다. Git 기준 버전과 미커밋 변경을 기록하고 사용자 변경을 보존한다. 전체 저장소 정밀 분석보다 다음 작업에 관련된 흐름과 의존성부터 조사한다.

문서에 적힌 의도, 코드의 구현, 실제 실행 결과를 구분한다. 주요 모듈·저장소·외부 연동·관련 테스트와 보존할 기능·데이터·인터페이스를 파악한다. 현 동작이 요구사항에 맞는다고 가정하지 않는다. 기술 부채는 온보딩이나 요청 변경에 관련된 항목만 기록한다.

## 변경 요청이 있을 때

현재 동작과 원하는 동작의 차이, 유지·수정·추가할 항목을 정리한다. 필요하면 requirements 지침을 연결하고 영향받는 모듈·사용 흐름·인터페이스·데이터·테스트와 완료 기준을 기록한다. 데이터 변경 등이 있을 때만 이전·복구 계획을 검토한다. 변경 요청이 없다면 현황과 작업 준비 상태를 정리하고 기능 요구사항을 만들어내지 않는다.

## 환경 재현과 검증

공통 코드 참조의 초기 셋업 절차로 문서화된 버전·설정·잠금 파일을 우선해 실행을 재현한다. 연결 대상이 로컬인지 확인하고 공유·운영 데이터에 쓰는 명령은 실행하지 않는다. 실제 통합 실행과 외부 연동이 막힌 상태의 부분 실행을 구분한다.

실패 원인은 근거가 있을 때만 기존 코드·환경·온보딩 변경으로 분류한다. 범위 내 환경 문제는 해결하되 넓은 코드 수정은 후속 계획으로 분리한다. 기존 README를 복제하지 않고 잘못되거나 누락된 실행 정보와 검증 근거를 보완한다.

## 인계

관련 시스템 구조, 유지할 규칙, 실행 명령과 검증 결과, 미확인 사항과 다음 작업을 기존 지식 기록에 남긴다. 변경 요청이 있으면 영향 범위와 검증 기준을 함께 연결한다. 과거 실행 결과를 현재 검증 결과로 재사용하지 않는다.
