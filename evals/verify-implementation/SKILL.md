# 구현

소프트웨어의 필수 산출물은 소스코드와 실행파일 또는 실행 패키지다. 소스 저장소·커밋, 빌드 명령·환경·의존성, 실행 산출물의 버전·대상 환경·실행 방법을 [작업 서식](assets/task.md)에 연결한다. 웹·스크립트는 해당 환경에서 실행 가능한 빌드 결과물·패키지로 정의하며, 소스만 작성하고 실행 산출물을 생성했다고 보고하지 않는다.

테스트 우선 개발을 요청했거나 프로젝트 규칙에 정해져 있으면 [TDD](../verify-tdd/SKILL.md)를 적용한다. 이슈→PR→병합까지 요청한 경우 전체 진행은 [ship](../verify-ship/SKILL.md)을 따른다.

작업 기준·검증·상태를 [작업 서식](assets/task.md) 또는 프로젝트의 기존 작업 원본에 기록한다.

작업 범위에 맞는 [프런트엔드](references/frontend.md), [백엔드·API](references/backend.md), [DB](references/database.md) 지침만 읽는다. 역할별 책임·입력·산출물·경계를 구현에 적용한다.

[공통 원칙](../../shared/core.md)을 읽고 요청 범위와 기존 결정을 따른다. 별도 실행이 필요하면 [위임 방식](../../shared/delegation-execution.md)을 적용한다.

입력: 범위·완료 조건, 관련 기능 ID·기획·설계, 작업 식별자.

1. 실제 상태·선행 작업·기존 변경을 확인하고 수행 계획을 정리한다.
2. 합의한 범위에서 결과물을 작성한다. 개발, 문서, CAD 등 해당 분야 역할과 도구를 선택한다.
3. 작성자가 테스트·실행·렌더링 등 산출물에 맞는 자체 검증을 한다.
   소프트웨어는 [테스트](../verify-test/SKILL.md)의 항목·결과·버그 연결을 사용한다. 빌드와 실행 확인 결과를 구분하고, 필수 도구·환경이 없으면 실행파일 미생성과 차단 이유를 명시한다. 테스트 단계에서 결함 수정으로 들어온 경우 필요한 수정·회귀 검증만 수행하며 전체 단계를 재귀적으로 반복하지 않는다.
4. [독립 검토](../verify-review/SKILL.md)를 요청하고 범위 내 결함을 수정·재검증한다.
5. 영향받는 기준·문서와 기능별 상태를 갱신하고 변경 내용·검증 근거·남은 제한을 보고한다.

판단 충돌·주요 변경·한도 도달 시 해당 작업을 보류한다. 재시도 횟수를 초기화해서 한도를 피하지 않는다.

완료: 수용 기준과 독립 검토를 통과하고 관련 기록이 일치한다. 배포·실물 반영은 [별도 절차](../verify-release/SKILL.md)다. GitHub Issues 사용 여부와 순차/병렬 정책은 프로젝트 설정을 따른다.
