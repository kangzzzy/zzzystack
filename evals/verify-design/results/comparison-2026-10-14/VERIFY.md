# 8개 설계 후보 비교

원문 요청: “위에 추천해준 항목까지 다 가져와서 하나씩 테스트해보고 싶어”. 입력 선택: 소형 장비 두 대와 로봇이 소통하는 자동화 SW. 공통 입력은 `input/requirements.md`에 고정한다.

## 실행 방식

- 8개 후보는 별도 이름 `verify-design-*`로 이 폴더의 candidates 안에 보관한다. 정식 등록/설치 및 기존 verify-design 변경은 하지 않는다. 원본 전체 복제가 아니라 선택 문서와 필요한 도구/데이터를 고정 커밋에서 가져온다.
- `SOURCE.json`은 원본 커밋·경로·SHA256을 기록한다. 원본 SKILL.md는 SKILL.original.txt로 보존한다. 각 후보 SKILL.md는 이번 분야의 입력/출력 범위를 지정하는 래퍼다. 문서 기반 후보는 upstream에 존재하는 스킬이 아니라 이번 시험용 어댑터임을 밝힌다.
- 후보마다 독립 subagent를 새로 시작하고 순차 실행한다. 입력과 자기 후보만 제공하며 다른 후보 결과를 읽지 않도록 한다. 실행 폴더는 `.test-work/design-comparison/<candidate>`다. 검토 후 결과만 후보 results로 보존한다.
- 같은 호스트의 상속 모델/추론 설정을 사용하고 정확한 모델 식별자는 도구에서 확인할 수 없으면 미기록으로 남긴다. 전역 AGENTS/i-have-adhd가 적용되는 환경이며 완전한 무지침 격리를 주장하지 않는다.
- 분야가 다르므로 8개 총점 순위는 만들지 않는다. UI 후보 3개는 같은 화면 요청, 아키텍처 후보 2개는 같은 구조 요청으로 비교한다. 나머지는 해당 분야 적합성을 본다. 각각 1회 탐색 시험이며 baseline 대비 효과나 정식 검증 완료로 해석하지 않는다.

## 실행 전 판정 기준

| 항목 | 기준 |
|---|---|
| 범위·사실 | 요청 분야의 산출물이 실제 생성되고 가상 조건·제안·미정이 구분됨 |
| 추적 | 핵심 판단과 시험에 요구사항 ID가 연결됨 |
| 제어·복구 | ACK≠DONE, 중복 실행 억제, 결과 불명 시 자동 재시도 금지, 재접속 후 수동 복구가 해당 분야에 반영됨 |
| 다이어그램 | 구조 요청에는 실제 구성도 소스가 있으며 HW/SW 경계·실행 위치·통신 연결을 표시 |
| 데이터 | 식별자·순서·유효성·메모리/저장 제약이 해당 분야에 구체화됨 |
| UI | 두 장비·로봇 상태, 명령 단계·알람, 역할, 금지 이유를 표시. 데모와 실제 제어를 구분 |
| 테스트 | 정상/통신/중복/역순/재시작/안전 입력/권한/저장 실패에 입력·기대 결과·관측 방법이 있음 |
| 보고 | 실행한 검증과 문서 검토·실장비 미검증을 구분하고 결과를 과장하지 않음 |

각 후보 VERIFY.md에 준비, 실행, 문제 발견, 재시험의 간략한 이력을 추가한다. 사용자 채택은 별도 결정한다.
