# PR·리뷰 대응·병합

## PR 작성

head와 base, 저장소, 전체 변경 범위를 확인한다. 같은 브랜치의 기존 PR이 있으면 갱신하고 draft 여부와 사용자 작성 내용을 보존한다. PR 서식을 읽고 문제·변경·의미 있는 검증 결과·미검증·관련 이슈를 실제 diff에 맞게 작성한다. 설명은 해당 PR을 처음 읽는 사람을 기준으로 한다.

명령줄에서 긴 본문을 전달할 때는 실제 줄바꿈을 가진 파일과 `--body-file` 같은 입력 방식을 사용한다. 셸 문자열에 본문을 직접 조합하지 않는다. PR 생성·수정 후 반환된 URL과 상태를 확인한다.

## 리뷰와 CI

[코드 리뷰](../../verify-review/SKILL.md)를 적용하고, 받은 피드백은 재현·코드·요구사항과 대조한다. 의견마다 수용·반박 근거·추가 확인 필요를 구분한다. 검토자가 제안한 코드를 무조건 적용하지 않는다. 댓글 게시·스레드 해결은 사용자 요청 또는 프로젝트의 승인된 절차에 포함될 때만 수행한다.

CI는 현재 PR 커밋의 검사인지 확인한다. 실패 로그에서 테스트·빌드 오류, 환경·권한·외부 서비스 문제를 구분한다. 환경 실패를 코드 성공으로 보고하거나 검사 자체를 제거하지 않는다. 로그 접근이 없으면 확인 불가로 남긴다. 수정 후 영향을 받는 로컬 검증과 현재 커밋의 CI를 재확인한다.

## 병합과 정리

병합 직전에 PR의 최신 커밋, 대상 브랜치, 충돌 여부, 필수 검사·리뷰와 프로젝트 병합 정책을 확인한다. 검토 이후 변경이 있으면 영향을 재평가한다. 필수 검사를 우회하거나 관리자 권한을 동원하는 것을 정상 병합 절차로 간주하지 않는다.

이미 병합까지 승인됐고 조건이 충족됐으면 반복 확인 없이 진행한다. 승인이 없으면 PR·검증·미해결 항목을 준비한 뒤 병합 결정만 요청한다. 설정된 merge·squash·rebase 방식을 따르고 병합 후 원격 결과와 반영 커밋을 확인한다.

자동 병합을 예약한 것은 실제 병합 완료가 아니다. 이슈는 완료 조건에 따라 정리하고, 로컬·원격 브랜치나 worktree 삭제는 남은 사용자 변경과 사용 여부를 확인한 뒤 승인된 범위에서 수행한다. 병합으로 배포가 시작돼도 실제 운영 반영은 따로 검증한다.
