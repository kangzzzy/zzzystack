# TDD

요구하는 동작을 테스트로 표현하고 실패를 확인한 뒤, 필요한 구현과 개선을 수행한다. 사용자 요청이나 프로젝트 규칙에 TDD가 있을 때 적용한다. 문서·서식 수정 등 동작 검증과 무관한 작업에 테스트를 억지로 추가하지 않는다.

## 준비

완료 조건, 관련 코드·테스트, 실행 방법과 기존 사용자 변경을 확인한다. 기존 테스트 도구와 관례를 사용하며 임의로 프레임워크를 추가하지 않는다. 관련 테스트의 현재 상태를 확인하고 기존 실패와 새 실패를 구분한다.

## 실패 → 구현 → 개선

1. **실패 확인:** 기대 동작을 관찰하는 가장 작은 의미 있는 테스트를 작성하고 실행한다. 예상한 이유로 실패하는지 확인한다. import 오류·환경 부족·잘못된 fixture로 실패한 것은 기능 실패 확인으로 인정하지 않는다. 실행하지 않았으면 실패를 관측했다고 하지 않는다.
2. **최소 구현:** 테스트가 요구하는 동작을 만족시키는 변경을 한다. 실제 동작을 구현하며 테스트 값만 하드코딩하거나 검증 기준을 약화하지 않는다. 해당 테스트를 다시 실행해 결과를 확인한다.
3. **개선:** 중복과 불필요한 복잡성을 줄이되 동작을 유지한다. 영향받는 테스트를 다시 실행한다. 다음 동작이 필요하면 같은 순서를 반복한다.

테스트는 외부에서 관찰 가능한 결과와 중요한 실패 조건을 검증한다. 내부 함수 호출 순서·문자열·구현 내용을 그대로 복제하는 테스트를 기본으로 삼지 않는다. 시간·난수·네트워크 등 결과를 불안정하게 하는 요소는 통제하고, 가짜 객체만으로 실제 연동이 검증됐다고 하지 않는다.

기존 구현이 이미 있다면 삭제해 TDD 순서를 재현하지 않는다. 버그 수정은 먼저 재현 테스트로 기존 결함을 확인한다. 추가한 테스트가 처음부터 통과하면 현재 동작 검증으로 보고하며, 과거에 실패했다고 꾸미지 않는다. 이후 필요한 동작 변경부터 실패 테스트를 작성한다.

## 완료와 한계

실행 명령·대상 동작·의도한 실패 원인·구현 후 결과·개선 후 결과를 간결하게 보고한다. 실행할 수 없는 환경에서는 테스트 초안과 미검증 상태까지만 보고하고 TDD 완료로 표시하지 않는다. 범위와 위험에 맞는 회귀 검증을 수행하되 관련 근거 없이 검사를 반복하지 않는다.

TDD 통과는 독립 코드 리뷰나 출시 완료를 뜻하지 않는다. 전체 구현 흐름은 [implementation](../verify-implementation/SKILL.md), 독립 검토는 [review](../verify-review/SKILL.md), PR·병합은 [ship](../verify-ship/SKILL.md)으로 연결한다. 이 스킬만으로 커밋·push·배포를 자동 실행하지 않는다.
