# 기술 설계 검토

Plan의 엔지니어링 매니저 관점 검토. 계획이 구현·검증 가능한지 확인한다. 상세 설계 작성은 [design](../../design/SKILL.md), 코드 변경의 검토는 [review](../../github/review/SKILL.md)을 사용한다.

[공통 원칙](../../zzzystack/references/core.md)을 읽는다. 웹 계획이면 [웹 아키텍처](../../design/references/web-architect.md), 데이터 모델 변경이면 [DB](../../build/references/database.md)를 필요한 범위에서 읽는다. 입력은 확정·미정이 구분된 제품 범위, 현재 코드·구조, 설계안과 제약이다.

1. 관련 코드와 기존 구조를 확인해 계획의 전제를 대조한다. 구현 사실, 제안, 확인하지 못한 부분을 구분하고 다른 분야에 웹 구조를 그대로 적용하지 않는다.
2. 컴포넌트 책임·인터페이스·데이터 소유권과 외부 의존성을 추적한다. 복잡한 흐름은 다이어그램으로 표현한다. 기존 기능 재사용과 더 단순한 대안을 먼저 비교한다.
3. 정상 경로뿐 아니라 입력 오류, 권한, 의존 서비스 실패, 재시도·중복, 동시성 등 해당 변경에 실제로 관련된 실패 경로를 검토한다. 데이터 변경이 있으면 호환성·마이그레이션·복구 계획을 확인한다.
4. 예상 부하와 데이터 규모에 근거해 성능·운영 제약을 확인한다. 근거 없는 규모 가정으로 구조를 확장하지 않는다.
5. 기능별 수용 기준을 테스트·관찰 방법에 연결한다. 중요한 정상·실패 경로, 테스트 수준, 필요한 데이터·환경을 명시하고 미확정 요구사항을 테스트 통과로 간주하지 않는다.
6. 착수 전 해결할 쟁점과 구현 중 확인할 사항을 구분한다. 범위·구조의 주요 변경은 대안과 비용을 설명하고 기존 승인과 충돌하는 결정을 자동 확정하지 않는다.

산출물: 구조·데이터 흐름 판단, 위험과 대안, 구현 순서·의존성, 수용 기준에 연결된 검증 계획, 미정 사항. 검토만 요청하면 원본을 수정하지 않는다.

완료: 구현 가능 여부와 조건, 남은 위험, 검증 방법이 명확하다. 테스트 계획을 실제 실행 결과로 보고하지 않는다. 자기 검토를 독립 검토로 표시하지 않으며 [Plan](../SKILL.md)으로 결과를 돌려준다. 코드 구현을 자동 시작하지 않는다.

gstack의 [plan-eng-review](https://github.com/garrytan/gstack/tree/main/plan-eng-review) 역할 구분을 참고해 zzzystack용으로 작성한 절차다.
