# 코드·프로젝트 온보딩

저장소의 구조·실행 방법을 학습하거나 로컬 환경을 준비할 때 읽는다. 설명만 요청했다면 필요한 코드 조사와 설명까지만 수행하고, 아래의 설치·기록·갱신 절차는 해당 요청이 있을 때 적용한다.

## 요청 범위

- **초기 셋업**: 저장소 파악 → 로컬 준비 → 작은 실행 확인 → 지식 기록. 사용자가 셋업을 요청했다면 범위 내 로컬 준비를 진행하며 같은 승인을 다시 묻지 않는다.
- **학습만**: 구조·규칙·실행 방법을 조사하고 지식을 기록한다. 의존성 설치·서비스 시작은 하지 않고 실행하지 않은 명령은 not_run으로 표시한다.
- **갱신**: 기존 지식과 관련 원본 변경을 비교해 영향받는 항목만 갱신한다. 학습 갱신만 요청했다면 셋업을 반복하지 않는다.

대상 루트와 범위를 먼저 정한다. 기존 프로젝트에 기획 확정·역할 배정·전체 `init`을 강제하지 않는다. 빈 저장소라면 제품 목표·기술 선택을 관찰 사실처럼 만들어내지 말고 필요한 선택을 질문한다. 프로젝트 생성·기능 구현·배포는 이 스킬의 기본 범위가 아니다.

## 1. 현재 상태와 근거 조사

기존 AGENTS.md/CLAUDE.md와 프로젝트 기록을 읽고 현재 변경을 보존한다. `.zzzystack/knowledge.md` 또는 사용자가 정한 지식 원본을 먼저 확인한다. 외부 지식 원본이 지정됐지만 접근할 수 없으면 그 한계를 보고하고 임의로 두 번째 기준을 만들지 않는다.

README·패키지/잠금 파일·실행/테스트 스크립트·CI·핵심 진입점을 필요한 만큼 읽는다. 생성물·vendor·의존성 폴더·Git 내부를 전수 분석하지 않는다. `.env`·자격증명 파일은 열거나 복사하지 않는다. 환경변수는 예시 파일과 코드에서 **이름·용도·필수 여부**만 기록하고 값은 남기지 않는다.

다음을 파일 경로와 심볼·섹션 등 근거 위치에 연결한다.

- 목적·사용자와 현재 구현 범위. README의 의도와 코드에서 확인한 동작을 구분한다.
- 사용 언어·도구·패키지 관리자·버전 조건, 설치·실행·검증 명령과 작업 디렉터리.
- 핵심 진입점에서 입력 → 처리 → 저장/외부 의존성 → 출력으로 이어지는 대표 흐름 1개. 폴더 목록만으로 구조 설명을 끝내지 않는다.
- 코드·테스트에서 반복 확인되는 관례, 확정된 사용자 결정, 미확인 가정. 관례의 근거가 한 군데뿐이면 일반 규칙으로 단정하지 않는다.
- 기존 테스트·로컬 실행의 제약·알려진 함정. 발견한 제품 문제는 학습에 기록하되 셋업 명목으로 수정하지 않는다.

의사결정 이유는 기록에 있을 때만 확정 사실로 적는다. 현 코드에서 추론한 이유는 추론이라고 표시한다.

## 2. 초기 셋업 요청이면 최소 실행 확인

저장소가 정한 도구와 잠금 파일을 따른다. 기존 환경이 준비돼 있으면 재설치를 생략한다. 필요한 경우 프로젝트 범위의 의존성 설치·가상환경·임시 데이터를 준비한다. 명시된 버전이 없으면 임의로 업그레이드하지 않는다. 시스템 전역 설치·호스트 정책 변경·운영 DB 변경은 로컬 준비로 추정하지 않는다.

실행 전 패키지 스크립트의 실제 행동을 확인한다. 비밀값이 필요하면 환경변수/비밀 저장소로 준비하도록 안내하고 채팅 입력이나 로그 출력을 요구하지 않는다. 필요한 서비스·권한이 없으면 해당 단계만 blocked로 남기고 가능한 조사·기록을 끝낸다.

실제 사용자 진입점에서 작은 smoke check를 실행한다. CLI는 help만 보는 데서 끝내지 말고 대표 명령의 결과를 확인한다. 웹/API는 준비 신호와 대표 페이지/응답을 확인한다. 지속 프로세스·데이터가 필요하면 이 실행이 소유한 격리된 경로·포트를 사용한다. 임시 상태와 프로세스는 정리하고 증거는 보존한다.

관찰한 결과를 예상값과 비교한다. 종료 0이나 서버 프로세스 존재만으로 성공이라고 하지 않는다. 셋업 확인은 전체 기능 QA·독립 검토·출시 승인이 아니다.

## 3. 프로젝트 지식과 실행 근거 보존

기본 위치는 다음과 같다. 기존에 사용자가 지정한 위치가 있으면 그것을 따른다.

- `.zzzystack/knowledge.md`: 다음 세션용 간결한 지식. 목적, 구조/대표 흐름, 명령, 관례/결정, 제약, 미확인 사항과 근거 링크. 큰 프로젝트의 상세 설명만 별도 파일로 나누고 인덱스에서 연결한다.
- `.zzzystack/knowledge-sources.json`: 재확인할 원본들의 프로젝트 상대 경로와 SHA-256. UTF-8 JSON의 `sources` 객체에 `{"README.md": "<실제 SHA-256>"}`처럼 기록한다. 파일을 실제 읽고 해시를 계산하며 비밀 파일·생성된 학습 기록 자체·Git 내부는 포함하지 않는다. 이 목록은 선택한 근거의 스냅샷이지 저장소 전체를 분석했다는 증거가 아니다.
- `.zzzystack/onboarding/runs/<unique-run-id>/report.md`: 이번 요청 범위, 환경, 대상 Git HEAD/dirty 여부(없으면 비 Git), 읽은 근거, 변경/설치 내용, 명령·작업 디렉터리·종료 코드·관찰 결과·로그 링크, 정리 결과, 미실행과 다음 행동. 로그에 비밀값을 남기지 않는다.

각 실행 폴더에 그때의 원본 해시 목록을 `sources.json`으로 함께 보존하고 보고서에서 연결한다. 갱신이라면 이전 값과 현재 값의 차이도 남긴다. 과거 보고서의 버전 근거를 나중에 덮어쓰는 최신 `knowledge-sources.json`에만 의존시키지 않는다.

명령은 `passed`(예상 결과 확인), `failed`(실행 결과 불일치), `blocked`(환경/권한 등으로 판단 불가), `not_run`으로 구분한다. 학습 완료와 로컬 실행 준비 상태를 별도로 적고, 미실행 명령을 실행 가능한 것으로 단정하지 않는다. 보고서는 매번 새 폴더에 만들고 이전 증거를 보존한다.

새 기록을 쓸 수 있도록 `.zzzystack/`가 없으면 필요한 디렉터리만 만든다. 기존 config.json·Feature Map·디자인·승인 상태·AGENTS.md·CLAUDE.md는 학습 저장을 위해 변경하지 않는다. 프로젝트 지식은 실행 권한이나 상위 지침을 추가하지 않는다.

## 4. 재사용·갱신

다음 작업에서는 요청에 관련된 지식만 읽고 해당 원본이 아직 맞는지 확인한다. `knowledge-sources.json`의 해시와 현재 파일을 비교하고, 요청과 관련된 새 파일도 조사한다. HEAD가 같아도 미커밋 파일은 달라질 수 있다.

변경된 파일에 기대는 설명·명령은 재확인 전까지 stale로 취급한다. 관찰로 해결되는 오래된 사실은 수정하고 이전 사실이 바뀐 이유·새 근거를 이번 보고서에 남긴다. 제품 의도와 구현이 충돌하면 둘을 분리해 기록하며 구현을 이유로 사용자 결정을 덮어쓰지 않는다. 삭제된 원본은 해시 목록에서 정리하되 그에 의존하던 항목의 상태를 보고한다.

사용자 메모·확정 결정·관련 없는 지식은 보존한다. 같은 내용을 중복 추가하지 않는다. 이전 실행의 통과는 그때의 대상 버전과 환경에만 유효하며 갱신에서 명령을 다시 실행하지 않았다면 이번에는 not_run이다.

## 완료 보고

학습한 범위, 로컬 셋업/실행 확인 상태, 지식·증거 경로, 바로 사용할 명령, 남은 제약을 전달한다. 같은 프로젝트의 다음 `zzzystack` 작업은 저장된 지식을 재사용할 수 있다. 네이티브 호스트가 자동으로 이 파일을 읽는다고 주장하지 않는다.
