# 제품 방향·범위 검토

Plan의 CEO·창업자 관점 검토. 제품 가치, 전략, 우선순위와 출시 범위를 다룬다. 기술 구조의 확정은 [기술 설계 검토](../verify-plan-eng-review/SKILL.md), 사용자 경험의 구체화는 [UX·디자인 검토](../verify-plan-design-review/SKILL.md)로 연결한다.

[공통 원칙](../../shared/core.md)을 읽는다. 입력은 현재 계획, 사용자 문제·근거, 목표·제약과 기존 결정이다. 계획이 없고 아이디어부터 탐색해야 하면 [문제 정의](../verify-office-hours/SKILL.md)를 적용한다.

1. 계획이 해결하는 문제와 성공 조건을 요약한다. 기능 목록보다 사용자에게 달라지는 결과를 기준으로 평가한다.
2. 사용자가 지정한 범위 모드를 따른다. 지정이 없으면 범위 유지로 검토한다. 확장은 더 큰 제품 가치 탐색, 선택적 확장은 효과가 큰 추가안만 비교, 유지는 현재 범위의 완성도 점검, 축소는 핵심 가치를 유지하는 최소 범위 탐색이다.
3. 문제의 중요성, 현재 대안 대비 이점, 핵심 가정, 첫 사용자 확보·학습 방법, 범위 대비 비용과 의존성을 확인한다. 사업 가설은 근거와 미검증 부분을 분리한다.
4. 주요 쟁점마다 현재 안, 대안, 추천과 이유를 제시한다. 더 큰 비전과 이번 출시 범위를 분리하고 추가 기능을 확정 요구사항에 자동 편입하지 않는다.
5. 기존 승인 범위 안의 계획 보완은 반영하고, 방향·범위의 주요 변경은 선택할 수 있는 구체안으로 제시한다. 기존 결정과 추천이 충돌하면 충돌을 드러내고 미정으로 남긴다.

산출물: 적용 모드, 제품 가치 판단, 유지·추가·제외 후보, 주요 가정과 검증 방법, 확정·보류 결정. 각 판단에 근거와 다음 행동을 붙인다.

완료: 출시 범위의 판단 근거와 미해결 결정이 명확하다. 사용자의 기획 확정은 [Plan](../verify-plan/SKILL.md) 기준을 따른다. 이 검토는 구현·배포 승인이나 독립 검토 통과를 의미하지 않는다.

gstack의 [plan-ceo-review](https://github.com/garrytan/gstack/tree/main/plan-ceo-review) 역할·범위 모드를 참고해 zzzystack용으로 작성한 절차다.
