# 문제 정의

Plan의 초기 탐색 스킬. 아이디어가 모호하거나 해결책부터 정해진 요청에서 사용자 문제와 검증할 가정을 구체화한다. 이미 확정된 계획의 범위 검토는 [제품 방향 검토](../plan-ceo-review/SKILL.md)를 사용한다.

[공통 원칙](../../zzzystack/references/core.md)을 읽고 기존 목표·결정·사용자 제약을 유지한다. 웹 서비스의 정책·기능 정의가 필요하면 [웹 기획](../references/web-planner.md)을 읽는다.

1. 기존 자료에서 대상 사용자, 문제, 현재 대안, 제약을 먼저 확인한다. 이미 답이 있는 질문을 반복하지 않는다.
2. 추상적인 선호보다 최근 실제 사례를 묻는다. 어떤 상황에서 문제가 생겼고, 현재 어떻게 해결하며, 시간·노력·실패가 어디에 발생하는지 파악한다. 핵심 불확실성부터 짧게 질문한다.
3. 관찰된 사실과 사용자 주장, 미검증 가정을 구분한다. 요청한 기능이 문제 해결과 어떻게 연결되는지 설명하고, 연결이 약하면 문제 정의의 대안을 제시한다.
4. 서로 다른 해결 접근과 각 접근의 제약·학습 가치를 비교한다. 기존 도구 활용이나 더 작은 범위로 확인할 수 있는지도 검토한다. 조사하지 않은 시장 수요나 구현 비용을 사실로 단정하지 않는다.
5. 추천 접근, 가장 작은 검증 방법, 관찰할 결과와 다음 결정을 정리한다. 사용자의 선택과 보류 사항을 구분한다.

산출물: 대상 사용자·문제 사례·현재 대안·근거와 가정·접근안·추천 이유·첫 검증 계획. 기존 기획 문서가 있으면 그 원본을 사용하며, 대화만 요청하면 파일을 만들지 않는다.

완료: 다음 기획 판단에 필요한 문제 정의와 남은 질문이 명확하다. 수요 검증이나 기획 승인을 대신하지 않는다. 필요하면 [Plan](../SKILL.md)으로 연결하며 구현을 자동 시작하지 않는다.

gstack의 [office-hours](https://github.com/garrytan/gstack/tree/main/office-hours) 역할 구분을 참고해 zzzystack용으로 작성한 절차다. gstack 실행 도구나 설치를 요구하지 않는다.
